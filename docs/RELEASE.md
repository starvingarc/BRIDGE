# 版本、公开发行与服务部署

## 当前开发版本

Python 包声明为 `0.3.0`，见 `pyproject.toml` 与 `src/bridge/__init__.py`。
这是已获准发行的私有单操作者研究版版本号；实际发行身份仍以主线提交、Git tag、构建校验和部署清单为准。不同提交可能沿用此版本号，
因此复现与问题报告必须同时记录 `git rev-parse HEAD` 和工作区是否有未提交改动。

前端 `package.json` 的 `0.1.0` 是私有前端包标识，不是 BRIDGE 产品发行号。
服务器历史 `rc.*` 由当次部署清单识别，也不能代替当前源码提交。
正式版本以经过发行流程的 Git tag、构建产物和资源绑定为准；合并 PR 不自动发行或部署。

## 开发、候选与部署通道

开发主线供获准协作者开发；候选版供指定验收者验证；正式私有版供获准的
单操作者研究用户使用；部署服务仅向该实例授权的操作者开放。代码权限不授予
真实数据访问权限，正式软件发行也不等于方法获得科学资格。用于正式科研分析时
仍须核对相应工具、资源、数据及测量合同的独立验证与授权边界。

| 通道 | 身份与用途 | 如何使用与验证 |
|---|---|---|
| 开发主线 | 持续集成的 `main`；记录准确提交和工作区状态 | 按开发指南配置，使用 `bridge-web --env development`；运行受影响测试 |
| 候选版 | 从明确主线提交构建的待验收产物，记录 SHA-256 与资源绑定 | 使用私有配置和 `bridge-web --test` 在独立 acceptance 环境验证；保存该产物的验收范围 |
| 正式版 | 完成对应软件验收、获准发行并有 Git tag／产物清单的版本 | 按发行流程核对构建与资源；版本号本身不能证明运行的是该产物 |
| 服务器部署标识 | 实际服务的部署清单、提交／产物摘要及资源组合；历史 `rc.*` 属于此身份 | 另行授权部署并检查健康、用户流程和恢复；不能由主线或候选测试状态推断 |

`bridge-web --print-version` 输出包版本；源码检出仍需记录 Git 提交与
工作区状态。启动参数和隔离规则以 [Web 启动说明](web-preview.md#start-a-private-instance)
为准，开发检查见 [开发指南](DEVELOPMENT.md#检查与内部验收)。
`--test` 是候选版使用的隔离启动模式，不自动执行验收、不晋级正式版或部署，
也不赋予科学资格。工程测试、模型输出质量、真实用户验收与独立科学验证分别记录。

## 0.3 私有研究版范围

0.3 收口于单操作者的单产品研究流程：五域测量、可追溯证据、获批公共文献、
生物学解释及受审查约束的修订、同版本研究报告。候选版修复了审查失败后缺少
原草稿与具体意见的问题，修订仍消耗原范围预算，并重新验证引用和内容一致性。
历史测量、解释与报告保留原版本；待修订稿只存在于私有会话中，不进入证据或报告。
大型轮次引用映射移至带 SHA-256 校验的私有旁文件，保留可重建的完整历史。
升级前备份整个会话目录；降级至旧格式软件时须恢复对应备份，不能只替换程序。

构建与真实运行须绑定准确提交和产物校验值。私有 0.3 的软件验收限定于
一个核心假设的生成、审阅、定点修订及同版本报告，已获准进行主线整合、发行和部署。
复杂多假设请求仍可能耗尽有限输出或超时；用户的发行许可不等于独立科学验证。0.3 不声明完整 PRD、多用户公网能力或科学资格；评分仍保持 shadow/unavailable，
不输出临床疗效、安全性或放行结论。总体未完成工作见[路线图](ROADMAP.md)。

## 内网多用户测试范围

开发代码提供显式启用的账号注册、会话所有权、管理员只读审计和个人模型配置。
面向获准内网，沿用 0.3.0 开发包版本；不扩大既有 tag 的验收声明。
新实例使用独立空白存储。旧会话清理、HTTPS、证书信任和允许网段按实例授权实施；
跨客户端可达性与代码检查分别记录。配置及恢复见 [Web 指南](web-preview.md#internal-multi-user-testing)。
该范围不构成公网多用户发行或独立科学验证。

## 三道独立关口

| 关口 | 需要回答的问题 |
|---|---|
| 内部软件发行 | 哪个已集成提交、构建产物和资源组合通过了哪些验证？ |
| 源码公开 | 代码、历史、文档、样例、贡献归属及资源是否获准公开？ |
| 公网部署 | 用户、数据、供应商、隔离、存储、运维和机构要求是否满足？ |

服务可以部署经过审核的私有发行版本，不必等论文发表；不能因此自动公开源码。当前预览服务不是公网多用户服务。

## 正常发行流程

日常分支和合并规则见 [CONTRIBUTING](../CONTRIBUTING.md)。发行流程为：已集成主线 → 候选版本 → 构建与准确资源绑定 → 对应范围的内部验收 → 用户验收 → 正式版本 → 部署。修复回到主题分支和主线，不原地修改已发布快照。

公开快照保留已有公开历史，通过审核后的单向内容导出更新；开发来源与公开提交的对应关系由维护者保留。源码更新本身不构成新 Release、服务部署或科学资格验证。

## 每次发行与分析记录

- 软件版本、准确 Git 提交、构建产物 SHA-256 或镜像 digest。
- 工具和环境版本、科学资源组合、reference 与模型版本、知识快照、MeasurementSpec。
- 输入内容摘要、分析版本、证据与图表的来源绑定。
- 变更、兼容性、工程／真实运行／科学验证分别达到的范围及已知限制。

软件版本与资源版本独立管理；尚未形成完整 resource lock 时明确记录缺口。当前前端、Python 包和服务器交付标识尚未统一，统一版本来源属于路线图阶段 4，不以修改目录名称掩盖差异。

## 私有到公开

公开发行前审查源码及可达历史、文档中的未发表结果、凭据、数据、资源许可和贡献归属。采用经批准的发行内容单向导出，不整库镜像私有历史或 PR 讨论，不改写已有公开历史。记录私有来源提交与公开提交／清单／产物之间的映射，二者提交号不要求相同。

保留项目 MIT 许可及已有第三方声明；资源是否可分发单独核对。公开软件包和镜像不包含用户数据、真实验收回执、访问口令或模型密钥。

## 部署与恢复

开发、预发布、生产环境分离；部署使用明确产物而非可变工作树。上线前验证用户隔离、大文件配额、后台任务恢复、删除与备份恢复。运行日志不默认保存完整模型上下文或原始科研 metadata。

每次升级保留上一版本、配置兼容说明和数据迁移／恢复方案。程序回退不等于会话或数据库回退。未来公网托管、域名、地区、预算、保留期限和机构审查在对应阶段决定，当前不预设供应商、不做合规认证声明。
