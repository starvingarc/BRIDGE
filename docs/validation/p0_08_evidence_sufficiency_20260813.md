# P0-08 Evidence Sufficiency candidate validation — 2026-08-13

## Biological question

The implementation asks whether immutable upstream evidence records for a declared ProductCase and domain can be folded through Data Readiness, Model Robustness and Prior Applicability without turning missing evidence into a biological failure or score.

## Data, references and controls

Validation uses synthetic JSON-only fixtures representing ProductCase/ProductDefinition pointers, MeasurementSpecV2, QCReadinessProfileV2, MeasurementResultV2, validation, prior-applicability and sensitivity records. It uses the packaged candidate gate rule and reason-code catalog. No expression matrix, real product, patient, private, locked, sealed or competitor data are used; no scRNA analysis is rerun.

Controls cover an adequate/frozen/applicable path, one-field perturbations for limited/insufficient/not-assessed states, deterministic and prior-not-required paths, required/supporting Evidence Family combinations, all eight raw MeasurementResultV2 states, paired upstream ToolRun provenance, malformed/unbound/legacy inputs, full ProductCase/ProductDefinition pointer reconciliation, cross-bound assay/status/tool/MeasurementSpec-version mismatches, ambiguous logical IDs, strict versionless-schema ref versions, recursive unsafe-reference screening, object-input-order invariance, exact source-byte identity for every input role, same-directory reuse, input mutation and existing-bundle drift.

## Observed finding and product-evaluation meaning

Synthetic contract tests show the executor applies the fixed order Data Readiness → Model Robustness → Prior Applicability → sufficiency and keeps domains independent. Contract-complete missing records produce a successful `not_assessed` profile, with missing reasons separated from blocking reasons, while malformed, cross-bound, pointer-conflicting, ambiguous-ID, version-invalid, checksum-invalid or unsafe-reference inputs fail eligibility without a scientific result or output bundle. Any bound MeasurementResultV2 in `missing`, `unknown` or `unavailable`, or without paired upstream ToolRun identity/state, also produces an explicit successful `not_assessed`; `negative` and `alert` remain distinct counts and do not become pass/fail. The v0.2 result carries one path-free top-level binding for every accepted StructuredInputRef: role, logical object ID, object version, Schema ID and exact source SHA-256. ProductCase/ProductDefinition remain honestly scoped as versioned pointers declared inside checksummed DomainGateInput; their object content is not consumed or validated. Per-profile and case-summary counts keep all eight states distinct and count domain-profile references, not independent evidence, votes or weights. The explicit unsafe-reference pattern contract recursively checks JSON keys and values for absolute paths, `~user` and POSIX/Windows home-variable paths, opaque or slash-form `file:` schemes, credential-bearing URLs, non-empty credential-named JSON members, colon/equal credential assignments and token forms. A single semantic name rule drives structured-key, URL-query, assignment and scientific/source-string checks. After compact normalization, exact auth names plus password/passphrase/passwd/pwd/secret/token/credential/passcode/pincode suffixes are sensitive; key suffixes require a database/DB/webhook/master/service/account/signing/encryption/decryption/private/SSH/API/access/client/consumer/secret qualifier at a stem boundary, while PIN requires an explicit auth/account/access/security/login/user/credential/verification/device context. Parameterized direct-adapter and public validate/run tests reject the reproduced password-like and machine-key forms as only `unsafe_scientific_reference`, do not echo matched content and publish no bundle; adjacent controls including `pin`, `cellPin`, `publicKey`, `capillaryKey` and `monkey` remain accepted. This is a finite, explicit publication-safety vocabulary rather than an arbitrary-secret detector. A novel undeclared alias is not itself a violation of the current contract; accepting it into the contract requires an explicit vocabulary, documentation and regression-test revision. Every source field actually copied into a public profile is checked against the shared module-local scheme/identifier shape helper during eligibility; invalid values yield `structured_input_schema_invalid`, and both direct-adapter and public SDK execution return a failed `ToolRunV2` without publication. Request-local input IDs, including IDs containing spaces, remain binding keys, and non-published source text remains governed only by its source schema. Public and direct-adapter v0.1 rejection uses the shared `tool_request_v2_required` code. Exact Evidence Family duplicates collapse; all distinct conflicting required representatives remain in provenance and are not voted or averaged. Different supporting records cannot improve, worsen or conflict with the required gate record.

Reversing only `object_inputs` order preserves the input hash, run ID, result object and every reusable bundle byte, including when the second invocation targets the first output directory. Every role retains its exact source checksum in `ToolRunV2.request`, the bundle manifest and top-level `source_object_bindings`, and every exact checksum participates in bundle identity. A source-byte change therefore changes the run even when its separately recorded canonical semantic checksum remains equal. Every returned artifact checksum verifies its file. Ordered gate-rule precedence is not normalized away.

Even the synthetic sufficient path emits `domain_score=null`, `score_state=unavailable` and `p0_score_contract_unavailable`. This establishes deterministic engineering behavior only; it does not establish that any real domain or product has sufficient evidence.
